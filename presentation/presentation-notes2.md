# LINK 발표자 노트 (10~15분)

## 1. 프로젝트 소개 — 45초
- LINK는 AI 기반 양방향 재능 거래 플랫폼입니다.
- 단순히 재능을 등록하고 거래하는 기능보다, 원하는 상대를 더 잘 찾게 하고 거래 과정의 안정성을 확보하는 데 집중했습니다.
- 팀 역할: 박진우(로그인/회원가입, 포트폴리오, AI 매칭), 백승호(재능/요청글, AI 임베딩), 남윤아(채팅, 거래).
- 연결 문장: “서비스를 만들면서 특히 세 가지 문제가 크게 보였습니다.”

## 2. 문제 정의 — 50초
- 키워드 기반 검색의 한계, 거래 중 동시성 문제, Cookie/토큰 저장 방식의 보안 트레이드오프를 핵심 문제로 정의했습니다.
- 기능을 많이 보여주는 대신 이 세 문제를 어떻게 해결했는지를 중심으로 설명합니다.
- 예상 질문: 왜 리뷰/평판은 제외했나? → MVP 기간 내 핵심 흐름과 안정성 확보를 우선했고 ADR로 결정 근거를 남겼습니다.

## 3. 서비스 Flow — 45초
- 로그인 → 글 작성 → AI 매칭 → 채팅 → 거래 흐름을 보여줍니다.
- 데모도 같은 흐름을 따라갈 예정이라고 미리 말하면 청중이 구조를 쉽게 기억합니다.

## 4. 시스템 아키텍처 — 55초
- Frontend Express Server는 정적 파일, /api proxy, CSP/runtime config를 담당합니다.
- Spring Boot가 도메인 로직을 담당하고 PostgreSQL/pgvector, Redis, Supabase Storage, Gemini를 목적별로 연결합니다.
- 예상 질문: 별도 Vector DB가 아닌 pgvector를 쓴 이유? → MVP에서 기존 PostgreSQL과 함께 운영해 복잡도를 낮추기 위해 선택했습니다.

## 5. 핵심 Backend 설계 — 45초
- AI, 거래, 보안 세 영역의 공통점은 한 기술에 모든 책임을 몰아주지 않았다는 것입니다.
- 다음 슬라이드부터 각각 문제 → 선택 → 결과 순으로 설명합니다.

## 6. AI Matching — 1분 20초
- SQL 키워드 검색만으로는 표현이 다른 글을 찾기 어렵습니다.
- 반대로 Vector 결과만 신뢰하면 이미 종료되거나 실제 조건에 맞지 않는 글이 들어올 수 있습니다.
- 그래서 Vector는 후보 탐색, SQL은 원본 검증, 서버 MatchScore는 순위, Gemini는 추천 이유만 담당하게 했습니다.
- LLM이 순위까지 결정하지 않게 한 이유는 재현성/테스트 가능성/비용 관리입니다.
- 정확도 수치는 아직 측정하지 않았으므로 발표에서 과장하지 않습니다.
- 근거: PR #68, #72.

## 7. 보안 — 1분 10초
- 토큰을 JS가 직접 다루면 XSS 발생 시 탈취 가능성이 커집니다.
- HttpOnly Cookie로 전환하면 JS 접근은 막지만 Cookie가 자동 전송되어 CSRF 위험이 커집니다.
- 따라서 CSRF Token, SameSite/Secure, CORS, CSP를 함께 적용했습니다.
- 예상 질문: HttpOnly Cookie면 XSS가 해결되나? → 토큰 탈취 위험은 낮추지만 XSS 자체를 막는 것은 아니므로 DOMPurify와 CSP를 별도로 적용했습니다.
- 근거: PR #64, #65.

## 8. 동시성 / Transaction — 1분 20초
- @Transactional은 원자성은 제공하지만 동시에 같은 행을 읽고 수정하는 경쟁 자체를 막지는 않습니다.
- Wallet, Trade, RequestPost에 PESSIMISTIC_WRITE를 적용해 동시에 진입하지 못하도록 했습니다.
- 요청글은 1회성이라 OPEN→IN_PROGRESS→CLOSED 상태 전이를 적용했고, DB Constraint를 마지막 방어선으로 뒀습니다.
- 예상 질문: 낙관적 락이 아니라 왜 비관적 락? → 금전/거래 상태처럼 충돌 시 재시도보다 선점해 순차 처리하는 편이 단순하고 안전하다고 판단했습니다.
- 근거: commit c2e3645.

## 9. 성능 — 55초
- 코드리뷰에서 N+1 하나를 발견했고 추적하면서 추가 N+1을 더 찾았습니다.
- 채팅방 30개 기준 약 92쿼리에서 고정 4쿼리로 줄였습니다.
- 게시글 목록도 findAll 무제한 조회 대신 Pageable + EntityGraph 기반으로 바꿨습니다.
- 응답시간 그래프는 측정 전이므로 비워둡니다.
- 근거: PR #73, #74.

## 10. CI/CD — 50초
- 로컬 환경 의존을 줄이기 위해 PR/push마다 Backend와 Frontend 테스트를 자동화했습니다.
- Backend CI에는 pgvector PostgreSQL 서비스를 띄워 실제 사용 DB 특성을 반영했습니다.
- CI는 GitHub Actions, CD는 Render Auto Deploy가 담당합니다.
- 현재 checkout에서 render.yaml / Dockerfile은 확인이 필요하므로 세부 구현을 과장해서 말하지 않습니다.
- 근거: PR #93.

## 11. Troubleshooting — 50초
- 보안, AI, 거래 모두 “기술 하나 추가”가 아니라 문제를 재정의하고 책임을 나눈 변화라는 공통점이 있습니다.
- 이 슬라이드는 세 사례를 다시 묶어 기억시키는 용도입니다.

## 12. Before / After — 50초
- AI 품질, API 응답시간, 동시성 테스트의 수치가 아직 없다면 절대 만들지 않습니다.
- 확인된 숫자인 채팅 쿼리 수, 그리고 구조적인 Before/After만 먼저 제시합니다.
- 추가 측정값은 발표 직전 확보 시 그래프 영역에 삽입합니다.

## 13. Demo — 2분 내외
- 로그인 → AI 매칭 → 결과 → 상세/채팅 → 거래 순으로 하나의 흐름만 보여줍니다.
- 라이브 실패 대비 스크린샷 또는 짧은 녹화본을 준비합니다.

## 14. 결과 및 회고 — 45초
- AI에서는 역할 분리, Backend에서는 정합성/동시성, 팀 협업에서는 ADR/PR/CI의 중요성을 배웠다고 정리합니다.
- “기능 수보다 문제를 나누고 책임을 배치하는 법을 배웠다”로 마무리합니다.

# 예상 질문 TOP 10
1. 왜 pgvector를 썼나요? → 기존 PostgreSQL과 통합해 MVP 운영 복잡도를 줄이기 위해.
2. Vector 결과를 바로 쓰지 않은 이유는? → 상태/가격/기간 등 실제 비즈니스 조건을 보장하지 못하기 때문.
3. LLM이 Ranking까지 하지 않는 이유는? → 재현성, 테스트 가능성, 비용, 응답 안정성.
4. HttpOnly Cookie면 XSS가 완전히 해결되나요? → 아니며 토큰 탈취 위험만 낮춤. 렌더링 sanitization과 CSP가 별도 필요.
5. Cookie 인증에서 CSRF는 어떻게 막았나요? → CSRF token + SameSite + Secure + CORS.
6. @Transactional인데 왜 Lock이 필요한가요? → 동시에 같은 상태를 읽고 수정하는 경쟁은 별도 제어가 필요.
7. 낙관적 락이 아니라 비관적 락인 이유는? → 거래/잔액 충돌 시 선점 후 순차 처리 전략이 더 적합하다고 판단.
8. 92→4 쿼리는 어떻게 나온 숫자인가요? → PR #74의 채팅방 30개 기준 쿼리 구조 분석 결과.
9. AI 품질은 어떻게 검증할 건가요? → Golden Set을 만들고 동일 입력으로 Before/After 추천 적합도와 응답시간을 비교할 계획.
10. CI에서 pgvector를 띄운 이유는? → 실제 애플리케이션이 vector extension을 사용하므로 로컬과 최대한 유사한 테스트 환경을 만들기 위해.
