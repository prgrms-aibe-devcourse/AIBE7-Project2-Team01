# 거래 정합성 및 임베딩 처리 개선 트러블슈팅

## 개요

요청글과 재능글의 서로 다른 거래 특성을 반영하고, 동시 요청에서 발생할 수 있는 중복 결제·중복 정산·잔액 불일치 문제를 방지했다. 또한 외부 AI 임베딩 호출을 DB 트랜잭션 커밋 이후로 분리해 거래 잠금 시간이 불필요하게 길어지지 않도록 개선했다.

## S: Situation | 상황

### 게시글별 거래 성격이 상태에 반영되지 않음

- 요청글은 한 명과 거래가 성사되면 종료되는 1회성 글이다.
- 재능글은 여러 구매자와 반복 거래할 수 있는 상시 판매 글이다.
- 기존 거래 완료 로직은 `TradeStatus`만 `COMPLETED`로 변경했다.
- 요청글은 거래가 완료되어도 계속 `OPEN`으로 남아 다른 사용자가 다시 결제할 수 있었다.

### 트랜잭션은 있었지만 동시성 제어가 없었음

기존 코드에는 `@Transactional`, 잔액 검증, 거래 상태 검증이 있었지만 다음 제어는 없었다.

- 거래·지갑·요청글 행 잠금
- 동일 거래의 중복 결제·정산 방지 제약
- 같은 요청글에서 여러 결제가 성사되는 것을 막는 DB 제약

따라서 두 요청이 거의 동시에 실행되면 모두 변경 전 상태를 읽을 수 있었다.

```text
요청 A: 거래 PENDING 확인
요청 B: 거래 PENDING 확인
요청 A: 결제 처리
요청 B: 결제 처리
```

`@Transactional`은 각 요청 내부의 원자성과 롤백은 보장하지만, 서로 다른 트랜잭션이 같은 데이터를 동시에 읽고 변경하는 것은 막지 못한다.

### 임베딩 호출이 원본 트랜잭션 안에서 실행됨

게시글 생성·수정·삭제 시 Gemini 및 VectorStore 호출이 DB 트랜잭션 안에서 동기 실행되고 있었다.

```text
게시글 저장
→ 외부 AI 응답 대기
→ VectorStore 반영
→ DB 커밋
```

외부 API 응답이 느려지면 DB 커넥션과 비관적 락을 오래 점유하고, DB 작업이 롤백됐는데 벡터만 남을 가능성도 있었다.

## T: Task | 과제

다음 조건을 만족하도록 거래 흐름을 개선하는 것이 목표였다.

1. 요청글은 하나의 결제된 거래만 허용한다.
2. 재능글은 거래 완료 후에도 `ACTIVE` 상태를 유지한다.
3. 동일 거래의 결제·완료·취소가 동시에 실행되지 않게 한다.
4. 같은 지갑의 잔액 변경을 순차 처리한다.
5. 애플리케이션 검증을 통과하더라도 DB가 최종적으로 중복 데이터를 거절한다.
6. 임베딩 장애와 지연이 원본 CRUD 및 거래 트랜잭션에 영향을 주지 않게 한다.
7. 기존 인증·채팅·스토리지·AI 매칭 구조의 변경은 최소화한다.

## A: Action | 행동

### 1. 요청글 상태 전이 명확화

`RequestPostStatus`에 `IN_PROGRESS`를 추가하고 상태 변경 책임을 엔티티로 이동했다.

```text
OPEN
→ 결제 완료: IN_PROGRESS
→ 거래 완료: CLOSED

IN_PROGRESS
→ 결제 거래 취소 및 환불: OPEN
```

추가한 주요 상태 전이 메서드는 다음과 같다.

- `startTrade()`: `OPEN → IN_PROGRESS`
- `completeTrade()`: `IN_PROGRESS → CLOSED`
- `reopenAfterTradeCancellation()`: `IN_PROGRESS → OPEN`
- `closeStatus()`: 거래 전 작성자 수동 마감
- `cancelStatus()`: 거래 전 작성자 취소

허용되지 않은 상태에서 전이를 시도하면 `INVALID_REQUEST_POST_STATUS` 예외를 발생시킨다. `TradeEntity`도 `PENDING → PAID → COMPLETED` 순서를 자체 검증하도록 변경했다.

### 2. 비관적 쓰기 락 적용

금액과 상태 정합성이 중요한 작업이므로 `PESSIMISTIC_WRITE`를 적용했다.

```java
@Lock(LockModeType.PESSIMISTIC_WRITE)
```

잠금 대상은 다음과 같다.

| 대상 | 적용 경로 | 목적 |
| --- | --- | --- |
| `ChatRoom` | 거래 생성 | 진행 중 거래 확인과 생성을 순차 처리 |
| `TradeEntity` | 결제·완료·취소 | 동일 거래의 상태 변경 중복 방지 |
| `RequestPostEntity` | 결제·완료·환불·수정·마감·삭제 | 1회성 요청글 선점과 상태 충돌 방지 |
| `WalletEntity` | 충전·결제·정산·환불 | 잔액 유실 갱신 방지 |

교착 가능성을 낮추기 위해 거래 처리의 잠금 순서를 통일했다.

```text
Trade → RequestPost → Wallet
```

요청글 결제는 다음 순서로 실행된다.

```text
거래 잠금 및 PENDING 확인
→ 요청글 잠금 및 OPEN 확인
→ 지갑 잠금 및 잔액 확인
→ 잔액 차감
→ 요청글 IN_PROGRESS
→ 거래 PAID
→ 커밋
```

두 결제가 같은 요청글에 동시에 접근하면 첫 번째 트랜잭션만 `OPEN → IN_PROGRESS` 전이에 성공한다. 두 번째 트랜잭션은 잠금 해제 후 `IN_PROGRESS` 상태를 확인하고 거절된다.

### 3. 요청글과 재능글 거래 흐름 분리

요청글은 거래 상태에 따라 게시글 상태를 함께 변경한다.

- 결제 성공: `OPEN → IN_PROGRESS`
- 거래 완료: `IN_PROGRESS → CLOSED`
- 결제 후 취소: 환불 후 `IN_PROGRESS → OPEN`

재능글은 반복 판매가 가능하므로 거래 완료·취소와 무관하게 `ACTIVE`를 유지한다. 작성자가 직접 판매를 중단할 때만 `INACTIVE`로 변경한다.

### 4. DB 중복 방지 제약 추가

애플리케이션 락과 별개로 DB를 최종 방어선으로 두었다.

- 동일 채팅방·사용자 참여 중복 금지
- 동일 채팅방의 `PENDING`·`PAID` 거래는 최대 한 건
- 동일 요청글의 `PAID`·`COMPLETED` 거래는 최대 한 건
- 동일 거래·지갑 거래 유형 조합 중복 금지
- 요청글 ID와 재능글 ID 중 정확히 하나만 설정
- 거래 금액은 0보다 커야 함
- 결제자와 수취자는 서로 달라야 함

신규 DB용 스키마는 [`../database/schema.sql`](../database/schema.sql)에 반영했다. 기존 DB용 SQL은 [`../database/migrations/20260831_trade_integrity_constraints.sql`](../database/migrations/20260831_trade_integrity_constraints.sql)에 분리했다.

현재 프로젝트에는 Flyway가 없으므로 기존 DB의 PostgreSQL 부분 유니크 인덱스는 마이그레이션 SQL을 직접 실행해야 한다.

### 5. 임베딩을 AFTER_COMMIT 이벤트로 분리

도메인 서비스가 `EmbeddingService`를 직접 호출하지 않고 임베딩 이벤트를 발행하도록 변경했다.

```text
원본 DB 변경
→ 임베딩 이벤트 발행
→ DB 커밋 성공
→ AFTER_COMMIT 리스너
→ 별도 스레드에서 Gemini 및 VectorStore 처리
```

트랜잭션이 롤백되면 이벤트 리스너가 실행되지 않는다. 비동기 스레드에는 JPA 엔티티 대신 필요한 값만 복사한 `EmbeddingDocumentSnapshot`을 전달해 지연 로딩 오류를 방지했다.

요청글 거래에도 다음 규칙을 연결했다.

- 결제 성공: 요청글 임베딩 삭제 이벤트
- 결제 후 취소: 요청글 임베딩 재등록 이벤트
- 거래 완료: 결제 시 이미 삭제됐으므로 추가 처리 없음
- 재능글 거래 완료: 상시 판매 글이므로 임베딩 유지

임베딩 실행기는 이벤트 순서가 뒤섞일 가능성을 줄이기 위해 단일 스레드와 제한된 대기열을 사용한다.

### 6. 테스트 추가 및 회귀 검증

다음 내용을 단위 테스트로 확인했다.

- 요청글 정상 상태 전이와 잘못된 전이 거절
- 거래 결제 전 완료 거절
- 완료 거래 취소 거절
- 요청글 결제 시 `IN_PROGRESS` 전환
- 요청글 완료 시 `CLOSED` 전환
- 결제 후 취소 시 `OPEN` 복구와 환불 호출
- 이미 선택된 요청글의 추가 결제 거절
- 잠금 Repository 경로 사용

전체 Gradle 테스트와 Spring ApplicationContext 검증도 함께 수행했다.

## R: Result | 결과 및 배움

### 개선 결과

- 요청글의 1회성 거래 규칙이 코드와 DB에 함께 반영됐다.
- 동일 거래의 중복 결제·완료·취소 요청이 행 잠금으로 순차 처리된다.
- 지갑 잔액 변경이 직렬화되어 유실 갱신 위험이 줄었다.
- 재능글은 거래 완료 후에도 판매 상태와 검색 가능 상태를 유지한다.
- 임베딩 지연이 원본 DB 트랜잭션과 거래 잠금 시간을 늘리지 않게 됐다.
- 원본 트랜잭션이 롤백되면 임베딩 이벤트도 실행되지 않는다.
- 현재 기준 전체 백엔드 테스트 40개가 통과했고 ApplicationContext가 정상적으로 기동됐다.

### 배운 점

- `@Transactional`은 동시성 제어 자체가 아니므로 금전·상태 변경에는 별도의 잠금 전략이 필요하다.
- 비관적 락은 같은 잠금 순서를 지켜야 교착 가능성을 줄일 수 있다.
- 요청글과 재능글처럼 생명주기가 다른 도메인은 동일한 거래 후처리를 공유하면 안 된다.
- 애플리케이션 검증과 DB 제약을 함께 사용해야 경쟁 조건과 우회 입력을 모두 방어할 수 있다.
- 외부 API 호출은 가능한 한 DB 트랜잭션과 락 범위 밖으로 분리해야 한다.

## 남은 과제

- 기존 운영 DB에 거래 정합성 마이그레이션 SQL 적용
- 실제 PostgreSQL을 사용한 멀티스레드 동시 결제 통합 테스트
- 잠금 대기 시간 제한 및 타임아웃 예외 처리
- 클라이언트 재시도까지 고려한 결제 멱등성 키 도입
- 서버 종료 시 비동기 이벤트 유실을 방지하는 Outbox 및 재시도 구조
- DB 제약 위반 원인별 사용자 오류 메시지 세분화
